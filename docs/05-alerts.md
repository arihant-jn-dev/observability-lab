# Which alerts are worth waking up for

The alert rules are in
[observability/prometheus/rules/alerts.yml](../observability/prometheus/rules/alerts.yml).
This is the reasoning behind them.

---

## The one rule

> **Page on symptoms. Ticket on causes.**

A **symptom** is something a user can feel: requests failing, requests slow,
orders not being created.

A **cause** is a mechanism: CPU high, pool saturated, cache cold, memory
climbing.

### Why this is not pedantry

**There are ~5 symptoms and unlimited causes.** Alert on causes and you write
alerts forever and still get taken down by cause #47 that nobody predicted. A
symptom alert catches failures you *didn't* think of — you didn't predict the
mechanism, but you predicted that users would notice.

**Cause alerts fire when nothing is wrong.** CPU at 95% with latency fine is a
well-utilised machine, not an incident. Page on that and people learn to ignore
the pager — which is how the real outage gets missed at 4 a.m. three weeks later.

**Alert fatigue is a real failure mode, not a personality flaw.** Every
unactionable page erodes trust in every future page. The cost of a noisy alert
is not the interruption; it is the *next* alert being ignored.

Causes still earn their place — as **tickets**. They are what you look at after
a symptom fires, and how you catch slow degradation before users feel it. They
just must not wake anyone.

## The alerts that page

### `HighErrorRate` — >5% of requests 5xx for 2m
The most basic symptom. Note it is a **ratio**: 50 errors/sec is catastrophic at
100 rps and irrelevant at 100k rps. Every count-based threshold you set today is
wrong after your next good quarter.

### `HighLatencyP99` — p99 > 1s for 2m
p99, not mean. [With this lab's own data](02-percentiles.md), the mean read
310 ms while the typical user experienced no change at all — and would have read
the same 310 ms if *everyone* had been moderately slow. The mean cannot
distinguish those, so it cannot be alerted on.

### `OrdersStopped` — checkout traffic exists but zero orders created
**The most important alert in the file.**

Every other alert can be green while the business is dead. A deploy that makes
checkout silently return an empty cart produces: error rate 0%, latency
excellent, CPU low, all dashboards green, revenue zero. Only a **business
metric** catches that class of failure.

Note the guard:

```promql
sum(rate(orders_created_total[10m])) == 0
and
sum(rate(http_server_request_duration_seconds_count{http_route="/checkout"}[10m])) > 0.05
```

Without the `and`, this pages every quiet night. "Zero orders" is only alarming
when traffic exists — that is the difference between *quiet* and *broken*.

**If you take one idea from this document:** instrument the thing the business
would page you about, not just the thing the framework measures for free.

### `QueueLagGrowing` — p99 job lag > 30s
Async work has its own user-visible symptom. The request succeeded; the work
didn't happen. Note it alerts on **lag**, not depth — a fast worker keeps depth
near zero while badly backed up. Lag is what the user actually waits.

### `ServiceDown` — `up == 0`
`up` is generated by Prometheus, not the app, so it works when the app is too
broken to emit anything. **This is the argument for pull over push**: a push
system that goes quiet is indistinguishable from a healthy system with no
traffic. Silence is not a signal; a failed scrape is.

## The alerts that only ticket

| Alert | Why it must not page |
|---|---|
| `DbPoolSaturated` | Real and important, but it is the *cause* of a latency symptom that already paged. Alone it may be harmless. |
| `CacheHitRatioCollapsed` | Note it fires on a **sudden drop**, not a low value. Low is workload-dependent and fine; a drop precedes the DB getting 20× its normal load. |
| `RedisEvictingKeys` | Silent data loss — nothing errors, the app just sees more misses. Worth a ticket precisely *because* nothing is "broken". |
| `ContainerNearMemoryLimit` | Catches a leak before the OOM kill. Deliberately measured against the **container limit**, not heap — see below. |
| `EventLoopBlocked` | Node saturation. Diagnostic gold when paired with a latency page, meaningless alone. |
| `PrometheusCardinalityGrowing` | Your instrumentation degrading your monitoring. See [04-cardinality.md](04-cardinality.md). |
| `CollectorDroppingData` | If the pipeline silently drops, dashboards lie by omission and a "traffic drop" may be fiction. |

### Why `ContainerNearMemoryLimit` uses container memory, not heap

This is not a stylistic choice. [Measured in this lab](exercises/06-memleak.md),
during an off-heap leak:

```
container memory   162 MB → 344 MB     climbing toward the 512M limit
v8js heap used     FLAT                completely unmoved
```

An alert written against `heapUsed` — the metric most Node dashboards show —
**would never have fired**. Alert at the boundary that actually kills you.

## Thresholds, `for`, and the two ways to be wrong

Every alert trades false positives against slow detection.

- `for: 2m` on error rate — a 30-second blip is not an incident. Without a
  `for` clause you page on every transient. Too long and you are late. Ours are
  aggressive (2m) so the exercises fire promptly; production is usually 5–15m.
- `for: 5m` on `OrdersStopped` — needs a longer window because low order volume
  is normal at some hours.
- `for: 1m` on `ServiceDown` — a down target is unambiguous. React fast.

**Where thresholds should come from:** your baseline, not intuition. Run
[`01-baseline.js`](../load/k6/01-baseline.js), record p50/p99/hit-ratio/lag while
healthy, then set thresholds relative to *that*. Numbers picked from feel are
either never-firing or always-firing, and you find out which during an incident.

## What we deliberately did NOT alert on

Just as instructive as what we did:

- **CPU utilisation.** High CPU with good latency is a well-utilised machine.
  Alerting on it pages you for success.
- **Memory utilisation in the abstract.** Only *approaching the limit* matters.
- **Cache hit ratio being low.** Only a *drop* matters.
- **Individual slow queries.** During the N+1 exercise there are none — every
  query is sub-millisecond. A slow-query alert is blind to the single most
  common ORM performance bug.
- **Error *count*.** Ratios only.
- **Disk space** — omitted only because this is a lab. On a real system it is
  one of the few cause-alerts genuinely worth paging on, because it is
  predictable, unrecoverable once hit, and takes everything down at once.

## Where to go next: SLOs and burn rates

The natural evolution of `HighErrorRate` is a **multi-window burn-rate alert**.
Instead of "error rate > 5% for 2m", you define an availability target (say
99.9% over 30 days), which gives you an *error budget*, and you alert on how
fast you are consuming it:

- burning 14.4× budget over 1h → page (you'll exhaust the month in ~2 days)
- burning 6× budget over 6h → ticket

This fires fast for severe outages and stays quiet for slow trickles that stay
within budget — which is exactly the behaviour you want and which a fixed
threshold cannot give you. Requires a stated reliability target, which is a
product decision, not a monitoring one. That is why it is the next step rather
than this step.

---

## Checklist for any new alert

1. Would a **user notice**? → symptom → may page.
2. Is it **actionable right now**? If the answer is "look at it tomorrow", it's a ticket.
3. Is it a **ratio**, not a count?
4. Does it have a **`for`** clause?
5. Does the annotation say **what to do**, not just what happened?
6. Would it have fired during your last incident? Would it have fired on a quiet Sunday?
